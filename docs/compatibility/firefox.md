# Firefox

Retest drives Firefox 133.0.3 on macOS on Apple silicon over WebDriver BiDi, through its own client. The [guide](../guide.md#firefox) says how to configure a Firefox target. This page lists where Firefox ends a shared case otherwise than Chrome, and why.

All real Firefox runs used Firefox 133.0.3 build 20241209150345, started through Launch Services. The default route, which starts Firefox as a child process, has run only with a stand-in executable that speaks BiDi.

## Engine differences

Each item records what Firefox 133.0.3 or Retest's driver for it does. The shared browser suites hold a case one of them changes to the complete declared value, by deep strict equality. The conformance cases hold it to the status, failure class, operation, source line, literal message and required facts; A7 fills in only the failing event's own count of looks. A declaration that no longer holds, or that names no case, fails, also in a filtered run. Every declaration is in `tests/integration/engine-differences.ts` and cites its item here by number and by the bold words it opens with. A unit test fails when a declaration cites an item this page does not hold. A declaration is allowed only for a case that passes on Chrome, so a failure Chrome is meant to have cannot be relabelled as an engine difference. Chrome declares nothing.

1. **Typing is key by key, so a stopped fill names `keydown`.** WebDriver BiDi has no command that inserts text, so a fill types each character as a key and the input guard counts each one. When the page moves the focus after Retest focused the field, the guard stops the first event that would reach the page: `keydown`, where Chrome, which inserts text, stops `beforeinput`. The failure's `event` detail says which, and its class, message, the field's value and what the page received are as on Chrome. Case: `browser-actions`, "fill stops the typing when the focus moves", the value "Release checklist".
2. **Shift is a key of its own.** BiDi sets a modifier only by pressing its key, so an uppercase letter or a shifted symbol is typed with Shift held, and the page hears Shift go down before it, as it does from a person. Chrome's protocol sets Shift on the key event alone. Pressing `a`, `A`, `7`, `!` and `é` makes the page hear `a:KeyA: Shift:ShiftLeft:shift A:KeyA:shift 7:Digit7: Shift:ShiftLeft:shift !:Digit1:shift é::` (key, code, Shift held) where Chrome's hears no Shift keys. The field receives the same characters.
3. **Home moves no caret in a text field on macOS.** Firefox follows the system's key bindings, where Home scrolls and leaves the caret where it is. Typing `abcd`, then Home, then X gives `abcdX`, where Chrome and WebKit give `Xabcd`. Shift with Home still selects to the start, so Shift+Home then X gives `X` on every engine.
4. **A multiple select that needs keyboard moves is refused.** The toggle plan presses Space on whichever option holds the list's native focus, and neither the page nor BiDi shows which one does, so a move that did not land would select an option nobody asked for. Every keyboard choice in a `<select multiple>`, a single option among them, is refused before any key: "Could not select … in getByTestId('toppings'): Firefox cannot verify the native option holding keyboard focus before toggling it. A move can leave that focus unchanged, so Retest refuses multiple-select keyboard input before an unrequested option could be selected. Retest sent no input." The selection stays as it was. Cases: `browser-actions`, "a list chooses exactly those options of a select multiple"; conformance A5. A5 is `error`, `unsupported` at `select`, with `inputSent: false`, at the line choosing Olives and Basil, within 1000 ms. Its full message is "Could not select ['Olives', 'Basil'] in getByLabel('Toppings'): Firefox cannot verify the native option holding keyboard focus before toggling it. A move can leave that focus unchanged, so Retest refuses multiple-select keyboard input before an unrequested option could be selected. Retest sent no input." Use an unchanged selection here, or run a changing multiple-select case on Chrome or WebKit.
5. **One wheel event moves at most one page.** A scroll is one trusted wheel event carrying the whole delta, as on Chrome, and Firefox scrolls an element by at most a page for it. Turning the wheel 2000 pixels on the scroll page's 120-pixel terms box moved the terms by 108 pixels in each of five tries, with one wheel event heard, so Accept stays disabled; on Chrome the same scroll reaches the end. Splitting the delta into many events was tried and removed: the page then heard dozens of wheel events for one requested turn. Cases: `browser-actions`, "the wheel turned on the terms scrolls them to their end"; conformance A7. The shared click is `not_actionable`, "Could not click getByTestId('accept') within 2000 ms: it is disabled.", with `check: 'enabled'`, `covering: null` and `waitedMs: 2000`. A7 is `failed`, `check_failed` at `toBeEnabled`, "getByTestId('accept') is disabled. Looked {looks} times in 1500 ms.", where `{looks}` must equal its failing event's count and the assertion must use its whole budget. To reach the end, make separate scrolls of no more than the box's height.
6. **No phone or touch screen.** A Firefox target takes a viewport and pixel ratio. Firefox 133 accepts `devicePixelRatio: 2.625` through `browsingContext.setViewport` and reports that exact ratio, so a pixel ratio is not refused. Touch, mobile layout and another user agent remain refused. The phone case asserts `unsupported` and the full message "Firefox cannot emulate a touch screen, a mobile layout through WebDriver BiDi in the release Retest drives. A Firefox target takes a viewport, and no device." Use a desktop viewport and pixel ratio for Firefox; run a phone-layout test on an engine that supports it. Case: `browser-actions`, "a scroll delta is in CSS pixels, also on a phone page".
7. **Roles and names Firefox's tree computes its own way are refused by name.** `tests/integration/firefox-roles.test.ts` reads Chrome and Firefox side by side across 286 pages: of 23733 lookups, it answers 21635 alike and refuses 2098 by name, and none differently. On the locators page an `<img alt="Logo">` whose source is empty did not load, so `getByRole('img', { name: 'Logo' })` is refused with "an image that did not load has different accessibility membership". Native tables with a visible caption or header belonging to that table, or an explicit table, grid or treegrid role, permit table, row, unnamed-cell and header lookups. Hidden or nested-table cues do not establish their parent's data-table semantics. A visible table without those cues keeps the exact layout-table refusal: "Could not look up getByRole('row'): native tables can be layout tables in Chrome and data tables in Firefox. Retest cannot judge this lookup on Firefox. Use a test id or text." The team-table regression requires all seven row texts, 24 cells, the Role header and the caption-named table. Raw Firefox returns seven rows, 24 cells, one Role header and no cell named Grace Hopper; Chrome also reads seven rows. The separate named-cell refusal remains because Firefox does not name cells from their text. Use `getByText()`, `getByTestId()` or an unnamed cell's position with `nth()`. Cases: `browser-locators`, "img Logo"; conformance F8.1a. F8.1a declares `error`, `unsupported` at `toBeVisible` on `getByRole('cell', { name: 'Grace Hopper' })`, with `role: 'cell'` and a refusal within 1000 ms, after the row and positional-cell checks. Its full message is "Could not look up getByRole('cell', { name: 'Grace Hopper' }): Chrome names a cell from its text, and Firefox's accessibility tree does not, so Retest refuses the lookup rather than find less on Firefox. Find it with getByText() or getByTestId(), or by its position with nth()."
8. **A failed navigation is told in Firefox's words.** An address nobody answers opens Firefox's error page, whose address names its reason, `about:neterror?e=connectionFailure`; the driver passes that word on: "Could not open http://127.0.0.1:<port>/: connectionFailure.", with `errorText: 'connectionFailure'`, where Chrome says `net::ERR_CONNECTION_REFUSED`. The class and the address without its query are as on Chrome. A mapping to Chrome's names would be a guess.
9. **A title keeps the control characters `document.title` keeps.** Firefox strips and collapses only ASCII whitespace in a title; Chrome's `document.title` also reads each C0 control character as a space. A title of `\x9BBell\t tab \x1B[2J ` reaches the parent as `\x9BBell tab \x1B[2J` on Firefox and `\x9BBell tab [2J` on Chrome, in the goto and in the navigation it tells. The parent cleans both to the same record.
10. **A page's script has no Navigation API.** Firefox 133 has no `navigation` global (`typeof navigation` is `"undefined"` in a page's script), so a page that listens for `navigateerror` throws instead and never hears that Retest cancelled its navigation. The refusal, the empty field, the page kept where it was and no typing anywhere are as on Chrome. Case: `browser-secrets`, "the page hears that its navigation was cancelled".
11. **A request the page starts as it leaves is cancelled.** In the shared fixture, an input handler sends a `fetch` without awaiting it and then sets `location.href`: Firefox cancels that request as the page leaves, and the server never received it in any of twenty tries, where Chrome's request arrives. The text reached the page once and the next document arrives, as on Chrome. Case: `browser-secrets`, "the text reached one request". A raw probe without Retest's input hold gave zero arrivals in five tries too. Await delivery before navigating when the request is required.
