# Waits and leftovers

This lane changed the value poll, the native assertion poll, the shared look loop, Deadline's rounded-up delay, the failure hold in ChromiumPage, the Chromium process's profile cleanup hook, and their tests. It also pinned diagnostic coverage and two interruption paths in the diagnostics integration file. Existing changes were preserved. No commit, dependency, download, benchmark, runner edit, capture edit, Firefox edit or WebKit edit was made. The Chromium process change is within Task 3's permission to repair a cause in browser source.

Logs and scratch copies are under `.retest/scratch-waits-and-leftovers/`. Heavy commands use `gate.sh`, which checks `pgrep -f benchmarks/run.ts`, runs `lockf -t 0 /tmp/retest-heavy-gate.lock <command>`, and retries a busy lock after sixty seconds. Its launched shell pids and commands are in `processes.log`. Unit commands were also preceded by that benchmark check.

## Task 2. Review of the previous shared-wait fix

Three defects were found and fixed with tests that failed first.

1. An early timer can start the shared loop's last read at 119.9 ms, and the read can finish at 120.1. Testing `reached` only after that read stops the loop without a read sent at or after the deadline. The new fractional-clock case uses 0.2 ms reads and waits that finish 0.9 ms early. It fails on the earlier shared-loop fix. A capped local pause now rechecks the clock before dispatch. The same edge is covered and fixed in the value and native polls.
2. `ChromiumPage.#execute` held every failure when `expired` was true. An ambiguous match returned at 9.5 ms of 10 was held; a later stop then replaced it with `interrupted`. `tests/unit/browser-page.test.ts` now proves this sequence. The hold at `src/browser/page.ts:444` applies to timeout-related results that claim the whole budget, not arbitrary failures. The existing whole-budget refusal, early timeout and cancellation tests all remain and pass.
3. `Deadline.waitToEndMs` could exceed Node's maximum timer delay. At a start of 1.01 and a budget of 2147483647, subtraction reads 2147483647.0000002; rounding up gave 2147483648. The new deadline test fails with that exact value in `logs/deadline-max-before.log`. The getter now caps the rounded-up delay at `maxTimeout`. Callers still check `reached` after waking, so the cap does not declare an early end.

The original `reached` comparison itself is appropriate. `remainingMs`, `expired` and command allocation remain unchanged. The fake-clock tests also bound the completed polls below 122 ms for a 120 ms budget, and a passing test pins immediate preservation of an unsupported failure in the last fractional millisecond after an earlier observation. The wait code adds only the remaining timer fraction and the final bounded read. Host event-loop stalls and a callback that ignores its own command timeout can still exceed a wall-clock limit; these loops cannot make blocked JavaScript preemptible. No real maximum-duration timer was run.

The analogous broad WebKit hold remains at `src/browser/webkit/page.ts:597`, outside this lane's ownership. It should be narrowed for non-time failures too. Its return after the hold also needs the same post-wait cancellation check as Chromium. No WebKit source was edited.

## Task 5. Stops before capture or collection completes

The two added integration tests pin the runner's current behavior and its persisted result. They use a fake browser and real collection/test subprocesses, not a native platform claim. The page-opening test aborts from `holdOpening`; it requires one interrupted test, status `error`, no diagnostics summary, no diagnostics start/finish event, and a closed fake browser. The collection test writes a parent-visible marker from the module before a top-level pause. The parent stops only after seeing that marker while collection is still pending. It requires the run and file interruption, no listed test, no test start/finish event and no browser launch. This avoids relying on the runner's buffered collection console output.

Both tests pass on the current runner in `logs/diagnostics-scopes-and-stops.log`. The guide at `docs/guide.md:1090,1128` says capture that never started or was interrupted while starting is unavailable. `docs/plans/public-beta/release-0.1.0.md:79,85,167` requires explicit capture status for interrupted output. My judgment: a test whose web pages are opening has already started an attempt, so omitting diagnostic status altogether does not meet that intent, especially with `requireComplete`. The test deliberately pins the omission today; it does not bless it as the release contract.

Required runner change, without inventing a capture or opening another page after cancellation: in both interrupted exits in `src/runner/run-session.ts:996-1004`, before returning, add unavailable summaries for each `prepared` entry with `runtime.kind === 'web'` that has not registered capture. Derive app and logical session identity from that map and `formatSessionId(described.attemptId, app)`, merge them with native summaries already returned by `finishNative`, and emit matching `diagnostics.finished` events. When capture is enabled, both kinds must say `unavailable` with `the run was interrupted before capture started`; when capture is disabled, they must say `disabled`. Keep the interruption as the test's failure. Do not claim a scope, artifact or `diagnostics.started` event for a collector that never started. This can be implemented inside the runner without waiting on an uncreated page. The integration test must then require those summaries and events.

The empty test list during unfinished collection does match the intent. The parent has no completed, trustworthy collected test list. The guide at `docs/guide.md:1839` explicitly requires a run-level interruption and report when a file is still loading; a file-level failure and an inspectable run satisfy that without inventing test results. No runner change is needed for the empty list itself.
