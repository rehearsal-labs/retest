# Firefox driver

The independent engine-differences review completed two consecutive green shared-suite rounds and two consecutive green conformance rounds on Chrome, Firefox and WebKit. It found and fixed Firefox's false pixel-ratio refusal, and reported an overbroad native-table row refusal. The follow-up [waits validation report](../reviews/fix-reports/waits-validation-report.md) records the narrowed table guard and its validation. Earlier driver-only counts below are historical.

All real Firefox evidence here uses Firefox 133.0.3 build 20241209150345 on macOS on Apple silicon through Launch Services. No recorded run has started a real Firefox through the default spawn route on any host. A stand-in executable exercises that route's launch, BiDi handshake, process ownership, output redaction, failure paths and cleanup. It is not evidence of real browser compatibility.

## Corrections with regression evidence

- Each lookup keeps its requested names in its own asynchronous context. Concurrent role looks cannot replace another look's names. Exact and loose names are confirmed against Retest's normalization.
- The role table exercises Chrome and Firefox beside one another across 286 pages. With the narrowed native-table guard, it answers 21635 of 23733 lookups alike and refuses 2098 by name, with zero silent differences. The earlier completed table answered 21593 alike and refused 2140; before those corrections there were 213 silent differences. Unsupported native semantics and name sources fail by name instead of returning a smaller or larger set. Current evidence is `.retest/scratch-waits-validation/logs/firefox-drivers-and-tables.log`; earlier evidence is `/tmp/retest-firefox-roles-final.log`.
- An origin-bound fill intercepts only the top document's navigation. It continues paused frame and other requests, then releases every request its own intercept held, including late events. The hold is armed before the fill's first look for its field, and each later look lets go what it held so far as the page's own: a navigation that starts before the look that readies the field is waited for, and one the field's focus starts, or a later one, is held and refused. Arming it only after readiness, as an earlier fix did, let a navigation started by the field's focus go through unheld; the shared secrets case then threw an internal protocol error and the page left. A document the field was readied in that goes before any key is sent now fails the fill by name with nothing typed.
- Role resolution, restored cookies, page setup and intercept arming consume their command's own deadline. Window creation is attempted once. An unanswered or rejected creation fails setup by name and removes its user context.
- A preload relay blocks keyboard input in a new document until that document has a guard. Input already dispatched when a document is replaced stays an unknown outcome unless the old guard supplied a completed verdict. It is never retried.
- Firefox 133 runs the preload script twice in the first document a new window opens, in two sandboxes under the same name, and sends every later call to one of them (seen in every probe of four windows; a window's second document ran it again in a sandbox of its first). The other sandbox's relay never got a guard, so it stopped every key as unguarded typing after the live guard had counted it as reached: the page heard nothing, and the fill answered `ok` with input `sent` on an empty field. This was the cause of the four-window failure and of the Enter, select and fill failures on a test's first page. The sandbox calls reach now claims its document with an event of a random type written into the script, and any other relay that hears it stops blocking. The relays are added once per document a sandbox runs in, and a guard left from an earlier document is dropped.
- The target window is activated before readiness; an activation failure sends no input and remains a named failure. One input turn for the whole browser, added for the four-window failure, was measured once the duplicate sandbox was fixed: ten runs of the four-window case and ten rounds of four fills at once lost no text with it or without it, so it was removed.
- A multiple select that requires native keyboard movement or toggles is refused before input. Firefox does not expose the native focused option, and prior probes showed a move that left focus unchanged. The shared suite and A5 now assert the exact unsupported outcome; they do not claim multiple-select success. An unchanged selection is read back without input. Single-select behavior remains subject to its existing tests.
- A scroll is one trusted wheel event carrying the whole delta, as on Chrome, and Firefox moves at most one page for it. An earlier fix split a large delta into many turns; the page then heard dozens of wheel events for one requested turn, and the shared case whose page loads more near its end loaded four times instead of once. The split was removed; reaching the end of a long text with one large delta stays a named Firefox difference.
- An implicit system app must match the pinned version and build. An explicit executable can differ and records its real identity. A damaged pinned cache fails setup without falling back. The installed-build lookup's missing, damaged and installed answers are integrated.
- Whole process-table readings are asynchronous snapshots. Launch Services watches rarely while the connection stands and wakes when it ends. Signals still recheck each recorded pid and start identity immediately before delivery. This last per-pid check is synchronous; it does not read the whole process table. The exit hook also retains that ownership check.

- One browser opens and closes its windows and tabs one at a time. Firefox 133 puts a new tab in its most recent window of any kind and reads that window's tabs first; a tab asked for while another window was still being built failed with `unknown error` ("TypeError: tabBrowser is undefined"). Eight pages opened at once on a fresh browser, four with a saved state restored through a background tab, failed three of the four in 3 of 3 launches before, and none in 3 of 3 after. This was the cause of the conformance case F3.1b's setup failure.
- `FirefoxPage` offers element identity (`readElements` around the shared keyed look, inside one lookup scope for all its locators, and `dispatchTo` through the shared pin). Keys live in Retest's sandbox of the document.

## Diagnostics

The collector subscribes to Firefox's network events only and names the console kind unavailable with its reason, through a hook the attempt's capture honours (`unavailable` on a collection, `withoutSource` in `src/diagnostics/attempt.ts`), so a strict console rule fails as "could not judge". The [console probe](../reviews/fix-reports/firefox-console-probe-report.md) separates the cases on Firefox 133.0.3. Strings, numbers, the plain data object and the DOM node left the marker untouched. A logged enumerable getter and a nested getter each changed the title in both trials with a log subscription; neither ran with no subscription or network alone. Log subscriptions ignored depth and serialization options. The same depth limit worked on a script result. Firefox serializes before delivery, so filtering entries for primitive arguments cannot prevent the page mutation. This is why the refusal remains, rather than a claim that every value runs page code.

`tests/integration/firefox-diagnostics.test.ts` proves the network capture on the real browser: the document named `Document`, a 404 and a 500 apart from a refused connection, a redirect of two hops linked hop to hop, a request that never ended marked pending, a secret in a path redacted with the query cut, no console record, and the page's getter never run. A dedicated worker's request is recorded as its page's: Firefox names only the browsing context, so the scope does not claim workers and its reason says so. Frames of another site are covered, as the shared diagnostics file showed.

The added serialization regression in `tests/integration/firefox-diagnostics.test.ts` checks value types, subscription depth options, an attempted primitive filter, and the script-result depth control. Its run and the shared Firefox diagnostics rerun could not acquire the heavy gate; both remain unverified in this pass. The raw matrix above completed, and 45 focused unit checks pass. Initial compiler errors in the new test were addressed with explicit Firefox-page instance checks, but the compiler retry also could not acquire the gate. The shared diagnostics tests require an unavailable console with the reason and no console or runtime-error record, alongside the network assertions. Playwright's Firefox uses its patched build and `Runtime.console` over its own Juggler protocol, not `log.entryAdded` over BiDi. Its console support does not establish a safe route for stock Firefox 133.0.3. No opt-in unsafe console capture is built.

## Engine differences

Each records what Firefox 133.0.3 build 20241209150345 or its driver does on macOS on Apple silicon. Item 7 separates data-table lookups from the remaining layout-table and named-cell refusals. The shared suites compare the complete declared value by deep strict equality. Conformance compares the status, refusal class, operation, source line, literal message and required facts. A7 substitutes only the failing event's exact look count in its literal message. A stale declaration or a declaration naming no asserted case fails, including in a filtered run. Chrome has no declarations. Every declaration cites its item here and is in `tests/integration/engine-differences.ts`.

The conformance declarations are limited to cases that normally pass on Chrome. An intentional Chrome failure cannot be relabelled as an engine difference by adding literal text and a source anchor; the resumed review demonstrated that gap with Chrome's A11 record and closed it with a failing-first check.

1. **Typing is key by key, so a stopped fill names `keydown`.** WebDriver BiDi has no command that inserts text, so a fill types each character as a key and the input guard counts each one. When the page moves the focus after Retest focused the field, the guard stops the first event that would reach the page: `keydown`, where Chrome, which inserts text, stops `beforeinput`. The failure's `event` detail says which, and its class, message, the field's value and what the page received are as on Chrome. Case: `browser-actions`, "fill stops the typing when the focus moves", the value "Release checklist".
2. **Shift is a key of its own.** BiDi sets a modifier only by pressing its key, so an uppercase letter or a shifted symbol is typed with Shift held, and the page hears Shift go down before it, as it does from a person. Chrome's protocol sets Shift on the key event alone. Pressing `a`, `A`, `7`, `!` and `é` makes the page hear `a:KeyA: Shift:ShiftLeft:shift A:KeyA:shift 7:Digit7: Shift:ShiftLeft:shift !:Digit1:shift é::` (key, code, Shift held) where Chrome's hears no Shift keys. The field receives the same characters.
3. **Home moves no caret in a text field on macOS.** Firefox follows the system's key bindings, where Home scrolls and leaves the caret where it is. Typing `abcd`, then Home, then X gives `abcdX`, where Chrome and WebKit give `Xabcd`. Shift with Home still selects to the start, so Shift+Home then X gives `X` on every engine.
4. **A multiple select that needs keyboard moves is refused.** The toggle plan presses Space on whichever option holds the list's native focus, and neither the page nor BiDi shows which one does, so a move that did not land would select an option nobody asked for. Every keyboard choice in a `<select multiple>`, a single option among them, is refused before any key: "Could not select … in getByTestId('toppings'): Firefox cannot verify the native option holding keyboard focus before toggling it. A move can leave that focus unchanged, so Retest refuses multiple-select keyboard input before an unrequested option could be selected. Retest sent no input." The selection stays as it was. Cases: `browser-actions`, "a list chooses exactly those options of a select multiple"; conformance A5. A5 is `error`, `unsupported` at `select`, with `inputSent: false`, at the line choosing Olives and Basil, within 1000 ms. Its full message is "Could not select ['Olives', 'Basil'] in getByLabel('Toppings'): Firefox cannot verify the native option holding keyboard focus before toggling it. A move can leave that focus unchanged, so Retest refuses multiple-select keyboard input before an unrequested option could be selected. Retest sent no input." Use an unchanged selection here, or run a changing multiple-select case on Chrome or WebKit.
5. **One wheel event moves at most one page.** A scroll is one trusted wheel event carrying the whole delta, as on Chrome, and Firefox scrolls an element by at most a page for it. Turning the wheel 2000 pixels on the scroll page's 120-pixel terms box moved the terms by 108 pixels in each of five tries, with one wheel event heard, so Accept stays disabled; on Chrome the same scroll reaches the end. Splitting the delta into many events was tried and removed: the page then heard dozens of wheel events for one requested turn. Cases: `browser-actions`, "the wheel turned on the terms scrolls them to their end"; conformance A7. The shared click is `not_actionable`, "Could not click getByTestId('accept') within 2000 ms: it is disabled.", with `check: 'enabled'`, `covering: null` and `waitedMs: 2000`. A7 is `failed`, `check_failed` at `toBeEnabled`, "getByTestId('accept') is disabled. Looked {looks} times in 1500 ms.", where `{looks}` must equal its failing event's count and the assertion must use its whole budget. To reach the end, make separate scrolls of no more than the box's height.
6. **No phone or touch screen.** A Firefox target takes a viewport and pixel ratio. The independent review found that Firefox 133 accepts `devicePixelRatio: 2.625` through `browsingContext.setViewport` and reports that exact ratio. Retest's extra refusal was a driver defect and was removed. Touch, mobile layout and another user agent remain refused. The phone case asserts `unsupported` and the full message "Firefox cannot emulate a touch screen, a mobile layout through WebDriver BiDi in the release Retest drives. A Firefox target takes a viewport, and no device." Use a desktop viewport and pixel ratio for Firefox; run a phone-layout test on an engine that supports it. Case: `browser-actions`, "a scroll delta is in CSS pixels, also on a phone page".
7. **Roles and names Firefox's tree computes its own way are refused by name.** The role table above lists them. On the locators page an `<img alt="Logo">` whose source is empty did not load, so `getByRole('img', { name: 'Logo' })` is refused with "an image that did not load has different accessibility membership". Native tables with a visible caption or header belonging to that table, or an explicit table, grid or treegrid role, permit table, row, unnamed-cell and header lookups. Hidden or nested-table cues do not establish their parent's data-table semantics. A visible table without those cues keeps the exact layout-table refusal: "Could not look up getByRole('row'): native tables can be layout tables in Chrome and data tables in Firefox. Retest cannot judge this lookup on Firefox. Use a test id or text." The team-table regression requires all seven row texts, 24 cells, the Role header and the caption-named table. Raw Firefox returns seven rows, 24 cells, one Role header and no cell named Grace Hopper; Chrome also reads seven rows. The separate named-cell refusal remains because Firefox does not name cells from their text. Use `getByText()`, `getByTestId()` or an unnamed cell's position with `nth()`. Cases: `browser-locators`, "img Logo"; conformance F8.1a. F8.1a declares `error`, `unsupported` at `toBeVisible` on `getByRole('cell', { name: 'Grace Hopper' })`, with `role: 'cell'` and a refusal within 1000 ms, after the row and positional-cell checks. Its full message is "Could not look up getByRole('cell', { name: 'Grace Hopper' }): Chrome names a cell from its text, and Firefox's accessibility tree does not, so Retest refuses the lookup rather than find less on Firefox. Find it with getByText() or getByTestId(), or by its position with nth()." The [waits validation report](../reviews/fix-reports/waits-validation-report.md) records each completed gate and any outstanding validation.
8. **A failed navigation is told in Firefox's words.** An address nobody answers opens Firefox's error page, whose address names its reason, `about:neterror?e=connectionFailure`; the driver passes that word on: "Could not open http://127.0.0.1:<port>/: connectionFailure.", with `errorText: 'connectionFailure'`, where Chrome says `net::ERR_CONNECTION_REFUSED`. The class and the address without its query are as on Chrome. A mapping to Chrome's names would be a guess.
9. **A title keeps the control characters `document.title` keeps.** Firefox strips and collapses only ASCII whitespace in a title; Chrome's `document.title` also reads each C0 control character as a space. A title of `\x9BBell\t tab \x1B[2J ` reaches the parent as `\x9BBell tab \x1B[2J` on Firefox and `\x9BBell tab [2J` on Chrome, in the goto and in the navigation it tells. The parent cleans both to the same record.
10. **A page's script has no Navigation API.** Firefox 133 has no `navigation` global (`typeof navigation` is `"undefined"` in a page's script), so a page that listens for `navigateerror` throws instead and never hears that Retest cancelled its navigation. The refusal, the empty field, the page kept where it was and no typing anywhere are as on Chrome. Case: `browser-secrets`, "the page hears that its navigation was cancelled".
11. **A request the page starts as it leaves is cancelled.** In the shared fixture, an input handler sends a `fetch` without awaiting it and then sets `location.href`: Firefox cancels that request as the page leaves, and the server never received it in any of twenty tries, where Chrome's request arrives. The text reached the page once and the next document arrives, as on Chrome. Case: `browser-secrets`, "the text reached one request". The independent raw probe, without Retest's input hold, gives zero arrivals in five tries too. Await delivery before navigating when the request is required.
