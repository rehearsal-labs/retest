# Agent sessions lane record

Phase 3 item 5 of [the 0.1.0 handoff](../release-0.1.0.md): the bounded agent session API on the same drivers, observations and command machinery as tests. Written 5 October 2026, and changed the same day by the fix round of the review of this lane (findings A-1 to A-10 in [the review](../reviews/phase-3-review-install-agent.md); see "Fix round" below) and by the element identity work after it (see "Element identity"). Every claim in the gate table names the test that proves it and the engines it ran on. A test against the fake browser is marked fake; a test against a real browser names the browser.

## What exists

The API lives in `src/agent/` and is the package's `./agent` subpath (`@rehearsal-labs/retest/agent`, source `src/agent/index.ts`, built `dist/agent/index.js` with its declarations). The guide's [agent sessions section](../../../guide.md#agent-sessions) is the user-facing description.

| File | What it holds |
| --- | --- |
| `src/agent/host.ts` | `AgentHost`: named targets, each on one engine; one browser per target, launched once by that engine's driver; `open` through `acquireResources` with the `SessionBudget` and `hostResources` a test run uses, never throwing and giving a grant back once; late browsers closed as they arrive; lost browsers closed after `lostBrowserGraceMs`; `stop`; `close`; option and request validation, the hold's cap, the secret allow-list and the saved state's owner and app |
| `src/agent/session.ts` | `AgentSession`: `act`, `observe`, `observePage`, `recipe`, `check`, `saveState`, `frame`, `frameSource`, `renew`, `end`; lanes; the hold; the caller's lease; ending and giving the lease back |
| `src/agent/identity.ts` | the detection of a driver's element identity (`ElementIdentity` in `src/browser/contract.ts`: `readElements`, `dispatchTo`), and the two pure rules beside it (`keepsPlace`, `sameRecipe`) |
| `src/agent/looks.ts` | the looks a session served, with the driver's element keys where it gives them, element references and the rules that refuse them |
| `src/agent/recipes.ts` | the durable recipe rules: by keys in one read, or the look's own locator in one read |
| `src/agent/checks.ts` | a host's required check run on a session's page through the runner's own `decideHostCheck`, with the runner's own identity |
| `src/agent/targets.ts` | targets, the drivers' own launchers, the engine a browser states |

What it reuses unchanged: the drivers (`launchBrowser`, `launchFirefox`, `launchWebKit` and their pages), `page.dispatch` and `page.execute` with the page command schema, `parseKey`, `selectCommandProblem`, `scrollProblem`, `locatorProblem`, `SessionBudget`, `acquireResources`, `ResourceLease`, `SharedLocks`, `hostResources`, `SecretFiller`, `Redactor`, `Requirements` (for check identity), `decideHostCheck` (for the check itself), `formatSessionId`, `formatObservationId`, `newAttemptId`, the drivers' `captureState`, `newPage({ storageState })`, `screenshot` and `frameSource`.

## Decisions

1. **Named target and engine.** A host names its targets, each with its engine. An open names both. A target on another engine is refused with `setup_failed` before anything is launched; a browser whose identity states another engine than its target's is closed and refused. An engine with no launcher given uses its own driver. No engine stands in for another.
2. **One browser per target, a context per session.** As a test run shares a target's browser, a host does too. A lost browser is launched again for the next session that asks. A lost browser is closed `lostBrowserGraceMs` (two seconds) after its loss, through its own driver's close, so its processes have had a moment to go on their own before the close reaps what is left, checking each is a process it launched, and removes the profile; a long-lived host collects nothing. A browser that starts after the host stopped waiting for it is closed as it arrives, and `close` waits for it within the setup and cleanup budgets and reports a close that failed.
3. **Leases through the resources table.** An open builds its needs (named locks, then one session for its owner), sorted by `compareNeeds`, and asks `acquireResources` with a scope of the host's own for each owner, so a refusal names only the asking owner's sessions in `heldBy` and counts every other in `heldByOthers`, test runs included. Refusals carry the runner's own words. A lock keeps sessions of one host apart; it is not a test run's lock. Everything after the grant ends in one place that gives the grant back exactly once, whatever threw; `open` never throws and never rejects, a launcher that throws before it returns included, and a failed launch is forgotten so the next open launches again.
4. **Session identity.** `formatSessionId(newAttemptId(), app)`. The session's owner record names the host's run id, the purpose in the place a test's id goes, the attempt and the app. The page is named with `identify` before it is handed over.
5. **The hold and the lease.** Every session has `holdMs`, at most the host's `timeouts.hold` (ten minutes by default; a request for more is refused by name); every call's budget is cut by what is left of it. A session that reaches it is ended as `held_too_long`. The caller holds the session through a lease, `timeouts.lease` (one minute by default): every call, at its start and at its answer, and `renew()` renew it, and a call still running holds it. A session that hears nothing for the whole lease is ended as `caller_silent`, with a `timeout` reason naming the lease, and gives its context and session back as any ending does.
6. **Ending.** Ending aborts every running call with the reason, stops every frame source handed out, waits up to a second for answers, closes the context within the cleanup budget and gives the lease back. Sessions come back at once when the context closed or the browser is gone, and only once the browser has gone when the context would not close, as the runner's rule for attempts says.
7. **Lanes.** An action needs the session to itself; looks, checks, saving state and recipes may overlap each other; frames overlap anything, since they send no input. A call that would overlap is refused with `concurrent_commands` and sends nothing.
8. **References.** A look lists up to 100 matches, each with `{ sessionId, observationId, element }`. Using one is refused, sending nothing, when it belongs to another session, names a look this session never served or no longer keeps (it keeps its last 32), was taken on an earlier document (a navigation that commits a new document advances the session's generation; a look that saw one commit while it was taken is born stale), names a place past its list, or when a fresh read of the look's locator no longer lists the same matches with the same text and visibility. A field's value and an element's state are not compared, since they change without changing which element it is. Showing the same text never makes two elements one, so a reference acts only on the element it names. On a driver that offers element identity (`ElementIdentity` in `src/browser/contract.ts`), the look keeps each element's key, the fresh read must show the look's node still at its place (refused `changed` otherwise, with the count in the words when the list itself changed), and the action is pinned to that node: a page that puts another node at that place while the action waits for its element is refused by the driver as `not_actionable` with `details.refused` `moved`, and no input goes. Chromium's page offers it. Firefox's and WebKit's do not yet, so on those a reference acts only when its look listed that one element, through the look's own locator with no pick at any step, so the driver's strict match refuses rather than acts on another element should the page add a match before the input goes. Refused there with `unpinned`: a reference into a look that lists more than one element, and one into a look whose locator keeps a match by its place. `session.pinsElements` says which rule a session is under.
9. **Durable recipes.** A reference becomes a recipe only when a read proves the recipe finds that very element; showing the same text proves nothing. No step may keep a match by its place. On a driver that keys elements, one read resolves the look's locator and the recipe at once: the look's node must still be at its place and the recipe must find exactly that node. On a driver that cannot, the only recipe one read proves is the look's own locator, when that read finds exactly one element; the read of the look is then the read of the recipe. On Chrome a recipe that finds another node is refused with `other-element`, and one that finds the referenced node by another locator is accepted. On Firefox and WebKit every recipe other than the look's own locator is refused with `unproven`. A caller that wants a recipe looks with it first, and asks for the recipe of the one element that look lists.
10. **Saved state.** `saveState` returns the driver's `captureState` with the session it came from, that session's owner and app, and when, to the host only. `open({ state })` restores it through `newPage({ storageState })`, and only for a session of the same owner and app; another is refused by name (`other-owner`, `other-app`). A session opened without it starts empty.
11. **Frames.** `frame()` is the driver's PNG screenshot, as encoded. `frameSource()` hands out the page's own contract frame source (`frameSource(identity)`), named with the session's record identity; a page without one is refused by name with `unsupported` and `details.engine`.
12. **Required checks.** A check's identity is `Requirements.forTest` over the one check, so it is the runner's: the requirement's version, the check's id, `page`, and the SHA-256 of its redacted content. A frozen requirement refuses a changed or unknown check with the runner's words. A check needs an id, may name no other app than the session's, and may hold no secret value. It reads the page through the runner's own `decideHostCheck`, the code a test's host check runs, so it looks, decides and words a result as a test does, and asks whether the browser is still there before each read.
13. **Secrets.** The host's secrets go through the runner's `SecretFiller`: typed only on the session's base URL origin and the origins listed, read only after the origin check. An open may name the secrets its session may type (`secrets`); a fill of any other is refused by name before the secret is read, and a name the host does not hold refuses the open. Every text an answer holds goes through the host's `Redactor`, and a locator holding a whole secret value never reaches the page.
14. **No events.** An agent session writes no JSONL events and no run folder. Its answers are its record. Event types for agent operations would be an addition to `src/protocol/events.ts`, outside this lane.

## Element identity

Built after the fix round from the element identity brief (`docs/plans/public-beta/codex/fix-round/element-identity.md`), for Chromium, while the Firefox, WebKit and native lanes were still editing their own files. The agent consumes it unchanged: `hasElementIdentity` finds the two methods on the page by name.

What exists, in the page code every engine shares:

- `src/browser/page-scripts.ts`: `keyedObserveFunction`, `observeKeyed(limit, queries, ...elements)`. It reads several queries in one call, each with the same `resolve` and the same observation as `observe` (both now read through one `observationOf` helper), and keys each listed element from a `WeakMap` held on Retest's own world for the life of the document. A key is a token the world draws with `crypto.getRandomValues` when it first keys an element, then a count, so a key read in an earlier document names nothing in a later one, whatever that one holds. `prepareFunction` takes an optional `intent.element`: when its one match is not that node it answers `{ status: 'moved' }` before it fits, focuses, scrolls or arms anything.
- `src/browser/locate.ts`: `locatorsArguments(locators, values)`, the several-locator form of `locatorArguments`. The role and label elements of every locator are found in the same document's world, one locator after another, and each step names which of them are its own.
- `src/browser/element-queries.ts`: `observeKeyed(world, locators, deadline)`, which refuses an answer that does not key every element it lists; the `moved` readiness; and `dispatchPinned(command, key, dispatch)`, which runs a driver's own `dispatch` with every readying look of that command pinned to the node, and refuses with `usage`, sending nothing, a command that names no element.
- `src/browser/actionability.ts`: `moved` fails the action at once, `not_actionable` with `details: { refused: 'moved', inputSent: false }`, with no wait for the node to come back.
- `src/browser/contract.ts`: `ElementIdentity`, `KeyedRead`, `KeyedReading`, which `src/agent/identity.ts` re-exports.
- `src/browser/page.ts`: `ChromiumPage implements WebSession, ElementIdentity`, with `readElements`, mapped as a look is (a lost, closed or dialog-held page, an unreadable selector, a shadow root, a timeout, a stop), and `dispatchTo`, which is `dispatchPinned` around its own `dispatch`.

Why the pin is a scoped value (an `AsyncLocalStorage` that `prepare` reads) rather than an argument: every action path of every driver readies its element through the shared `prepare` inside `waitUntilActionable` (Chromium's, Firefox's and WebKit's pages all do), so one scoped value reaches every readying look of one command, each key of a select included, without each driver carrying the key through its own action code and without changing `Session.dispatch`. The Firefox bridge already scopes its lookups the same way. A look of any other command never sees it: a unit case runs a pinned and an unpinned wait side by side and reads each look's arguments.

Proven on Chrome 154 through the page alone (`tests/integration/agent-identity.test.ts`, one browser for seven cases): a keyed read lists each locator exactly as `observe` does and keys each node alike in every read and every locator that finds it; a click pinned to one of two twins reaches that row only, and pinned to the other is refused `moved` with nothing sent; a pinned check and a pinned select reach their own row of two that show the same, and an uncheck pinned to another row is refused; a pinned check whose box the page keeps unchecked and moves, so that a box already checked takes its place before Retest reads the state, fails `not_actionable` with input sent and the state unconfirmed, where before the fix it answered that the check was done; a pinned fill waiting on locked fields that the page then sorts is refused `moved` and no field holds text, the keys read after showing the sort came after the first read; a key from the document before a reload is refused even after the new document keyed the same button; a command naming no element is refused, and an unreadable selector in a keyed read is named. Through the agent: the cases in the gate table below.

Breaks the cases catch, run on copies of the tree outside the repository (`/tmp/retest-identity-mutants/`): without the pin check in `prepare`, five cases fail (four driver cases and the agent's re-sort case); with one token for every document, the earlier-document case fails at the refusal itself, the old key clicking the button of the new document.

The reads that confirm a pinned `check` or `select` after its input read the pinned node only. `readChecked` and `readSelection` pass the pin (`pinnedKey()`) to `locatorArguments`, which carries it on the query as `element`; `checkedFunction` answers null and `selectionFunction` answers `lost` when the one element at the locator's place is another node. A check then stays unconfirmed until its time runs out and fails `not_actionable` with `inputSent: true`, its message saying the locator no longer found the element it clicked; a select falls back to what the guard read of the pinned select itself as its change arrived, and otherwise fails the same way. Another element's state is never the answer. The pin is read straight from the keys' store (`pinnedReadHelper`), so the selection function declares none of the keyed look's helpers and the WebKit list plan, which splices that function's body after its own copy of them, still parses. Shown failing before the fix on a copy of the tree (`/tmp/retest-confirm-before/`, `/tmp/retest-fix-agent/confirm-before-chrome.log`), and by two unit cases of `tests/unit/browser-element-identity.test.ts`.

### What Firefox and WebKit need

Nothing in the shared code: the pin, the keyed look and the pinned confirming reads are there. Each page needs the two methods and nothing else of its action code, since every action path readies through `prepare` and confirms a check or a select through `readChecked` and `readSelection`. The requirement each engine must meet, and show on its real browser: inside `dispatchTo`, every read that confirms an action reads the pinned node only, and a pinned node gone from its place, or a key that no longer matches, leaves the action with its input sent and its state unconfirmed, never another element's state. A page function of a driver's own that confirms or plans for the pinned element takes the key from `pinnedKey()`, through `locatorArguments(locator, values, pinnedKey())`, and refuses another node in its place:

- `src/browser/firefox/page.ts`, `FirefoxPage`: `implements WebSession, ElementIdentity`; `readElements(locators: readonly LocatorRecipe[], timeoutMs: number, signal?: AbortSignal): Promise<KeyedReading>`, built as Chromium's is, around `observeKeyed(this.#world, locators, deadline)` inside the bridge's lookup scope; `dispatchTo(command: BrowserCommand, key: string, timeoutMs: number, signal?: AbortSignal, commandToken?: number): Promise<DispatchedCommand>`, which is `dispatchPinned(command, key, () => this.dispatch(command, timeoutMs, signal, commandToken))`. `FirefoxBridge.resolving(locator, work)` (`src/browser/firefox/bridge.ts`) scopes one locator's role wants; a keyed read needs every locator's at once, so it needs a form that takes `readonly LocatorRecipe[]`, refusing by `lookupRefusal` on each and merging their `roleWants`. To confirm on Firefox: the sandbox realm's `globalThis` reaches `crypto.getRandomValues` and `WeakMap`, and a new document gets a new realm.
- `src/browser/webkit/page.ts`, `WebKitPage`: the same two methods, `readElements` around `observeKeyed(this.#world, locators, deadline)` with the lookup refusals its `observe` case applies, for each locator. The multiple-select list plan (`listPlanFunction`) must plan from the pinned select only; the WebKit lane was adding that (a `moved` plan status) while this was written. The case to carry over is `a pinned check whose element the page moves before Retest reads its state is not confirmed by the element now in its place` in `agent-identity.test.ts`, which runs on each engine once it pins.
- Then `pinningEngines` in `tests/integration/agent-harness.ts` names the engine, and every agent case and `agent-identity.test.ts` moves from the refusal rule to the pinned rule on it, with no other test change.

## Found in the drivers, for their lanes

- **Firefox, labelled password field.** `getByLabel('Password')` found nothing on Firefox and found the field on Chrome. The Firefox driver finds labelled fields through their roles (`labelledRoles` in `src/browser/firefox/accessible-names.ts`), and a password field has no role.
- **Firefox, label and role looks during this lane.** From about the middle of this lane, `getByLabel` and `getByRole('textbox')` looks on Firefox threw "Accessibility.queryAXTree got a response that could not be read: $.result.value[0].value[0].value expected string", later "unknown key", reproduced with `launchFirefox` and the page alone (`/tmp/retest-agent-probe/role.ts`); `getByRole('button')` answered. The Firefox lane was editing `page.ts`, `accessible-names.ts` and `input.ts` at the time. The agent flows look for fields by test id for this reason and the one above.
- **Firefox, typed input across contexts.** Earlier in this lane, with several contexts open in one Firefox, a `fill` answered `ok` with input `sent` while the field stayed empty: three of four parallel fills in two probes and two test runs, and the first context's fill once when four contexts were open and sessions typed one after another. Typing goes through `input.performActions` on the context. The final runs, after the Firefox lane's edits to `input.ts`, passed the concurrent typing case twice; after the Mac restart it failed in both runs, all four fields empty once. Reproduced without the agent, through `launchFirefox` and four Firefox pages alone filling a field at once (`/tmp/retest-fix-agent/firefox-four-fills.ts`, under the gate lock): in 5 of 5 rounds every fill answered `ok` with input `sent`, and in each round one to three fields held nothing (`/tmp/retest-fix-agent/firefox-four-fills.log`). A fill should never answer `sent` for text that did not arrive. Fixed in the Firefox driver after the Mac's restart: Firefox 133 ran the preload script twice in a new window's first document, and the copy that never got a guard stopped every key after the live guard had counted it. The script then gave 0 of 5 bad rounds, and the concurrent typing case passed in every later run (see `proofs/firefox-driver.md`).
- **Firefox, a check's last read.** A page read given 1 ms at the end of a check's time throws a `timeout` failure on Firefox, where Chrome answers. The agent check now looks again on such a read, as the runner's host checks do; this was a defect in this lane's code, found on Firefox and covered by a unit test.
- **Chromium, close after an outside kill.** `ChromiumBrowser.close()` after the browser's main process was killed from outside throws "Process group N contains processes whose launch ownership could not be verified; they were left alone" even six seconds later, while `pgrep -g N` shows the group empty from 200 ms on. Reproduced with `launchBrowser` alone (`/tmp/retest-agent-probe/chrome-close.ts`). The agent test loses Chromium through its launch record (`signalGroup`), as the driver's own lifecycle tests do, and loses Firefox and WebKit by their main process.
- **WebKit, frame source.** The WebKit driver now has `webKitFrameSource(identity)`, outside the contract's `frameSource`, because the capture source names hold no `webkit`. An agent session refuses a frame source on WebKit by name until the contract carries it; once it does, the session hands it out with no change here, and the refusal case will fail on WebKit to say so.

## Harness note

The capacity suite's first version ran its host program through `runHostProgram` (`tests/integration/participants-harness.ts`). That test then failed in the harness's `after` hook: its last-resort release called `signalGroup` on a browser group the run had reported, and `signalGroup` threw "Process group N has no recorded launch ownership in this process, so it was not signaled". The suite now runs its program through `RetestProcess` directly and checks release with `assertReleased`, which only asks whether each group is still there. An existing suite that uses `runHostProgram` (`resources.test.ts`, the reservation case) passed when run alone, so why the hook threw for this program alone is not settled.

## Not done

- WebKit's driver offers no element identity yet, so on WebKit references act only on a look's single element and recipes are only a look's own locator (see "What Firefox and WebKit need" above). Firefox's driver offers it since the fix round: `agent-firefox.test.ts` passed with the identity suite, 26 passed and 2 skipped by name.
- No events for agent operations, and no run folder.
- No accessibility survey of a page (role, accessible name and test id per element) for an agent to read at once: the drivers expose no such command, so a look reads one locator. It needs a driver command under `src/browser/**`.
- Popups, tabs, uploads, downloads and dialogs stay outside, as Release 1 says.
- Diagnostics are not started on agent sessions; the collectors belong to another lane.
- Native targets: the API opens web sessions only.
