File-finalization review fix: recordings supervise file work in a private child of the media binary. Copy, sync, exclusive publication and source unlink use the remaining finish budget. An overrun is `deadline_exceeded`, with the possible partial path and a message naming the publication path and any unknown filesystem outcome. No late result is accepted as `ok`. The `.copying` route never uses ordinary replacing rename; without exclusive rename it tries link-then-unlink and otherwise fails with the partial named. Thumbnail and live routes decode before passing through original bytes. Live decode refusals are counted in `failed` and the last frame/refusal is named in `watchEnded.message`.

Additive reply-pressure fix: `Bye.repliesDropped?: number` names normal replies dropped before `bye` was queued and is absent when zero. Any normal reply loss makes the process exit 2. Stderr receives a JSON `mediaReplyFailure` record for reply loss or a blocked writer, with `schemaVersion: 1`, `reason: 'replies_dropped' | 'stdout_blocked'`, `repliesDropped`, and `inFlightUnknown`; the latter counts a pipe write whose delivery cannot be established. The stderr record includes queued replies discarded at exit, which a queued `bye` cannot predict. The writer owns a separate close-on-exec stdout descriptor, so a blocked write cannot hold Rust stdout shutdown and encoder descendants cannot retain the reply pipe. No method or parameter changes.

Additive review fix: `FrameSequence.captureGapsOmitted?: number` counts omitted capture-gap details across the recording when their conservative bounds may overlap the requested interval. It is absent when no omitted gap can overlap. It is not an interval-exact count. A positive count means missing evidence and evaluation returns partial. The same warning is included in `message` for consumers that tolerate additive fields. Older strict protocol-2 clients reject replies carrying either new optional field because their schemas reject unknown keys; they cannot read such replies as complete. Ordinary replies without the fields retain their old shape. Run-folder schemaVersion remains 1 with no new event or persisted field; the missing-evidence reason uses its existing string field. Method signatures and protocol version 2 are unchanged.

Client and runner review fixes: MediaProcessOptions accepts optional `env` as the complete startup environment; without it, only PATH, TMPDIR and the fixed locale are passed, as mediaEnvironment supplies. It gains optional `maxPendingRequests` with default 128 and optional `signal` for cancelling startup. `maxPendingBytes` now bounds complete request messages of every kind, including headers and thumbnail payloads. Requests beyond the byte or pending-request limit are refused by name; frames report dropped at pressure. No message is partly admitted. After a write reaches backpressure, admitted control requests wait in a bounded queue until drain arrives; new frames are dropped until drain. The byte bound includes this queue and the pipe, and queue count is capped by maxPendingRequests. Shutdown ends stdin only after the admitted queue drains. Timed-out starts count against the pending cap until answered, preserving their requested identity/output for late replies. Other timed-out job ids retain at most 1024 entries. `ReplyReader.end(): void` rejects truncated EOF. A parser failure clears retained bytes and makes the reader terminal; the client consumes no further stdout and close rejects the protocol failure after owned cleanup.

Started and ended replies must match the requested run/attempt/test/app/session identity and exact requested video output with its container extension. A started frame-store path and an ended partial path must also belong to that output. Frame-sequence replies must match the requested recording id and interval. A mismatch fails the protocol and the recording becomes unavailable with the reason; it never supplies foreign evidence. Protocol version 2 and existing media method signatures are unchanged. `StartMedia`, the internal runner starter contract, gains an optional fourth `signal` argument after `env`; one setup budget covers discovery, start and readiness, and late startup results are closed before use.

Run-folder schemaVersion remains 1. `RecordingRecord.capture?` preserves the source `clockMapping`, achievedFps and captureMs. `RecordingClock.timestamp?` distinguishes host-arrival from target-paint timestamps; current source mapping is run-arrival with targetClock not-used, so current recordings say host-arrival. Screenshot-loop latency measures request-to-arrival uncertainty. Cadence over a restarted source includes its withheld intervals; latency means are weighted by capture count. Older strict run-folder readers refuse records containing these additive fields. No target paint-time mapping or every-paint guarantee is claimed.

Linux lifecycle correction: an `ended` recording can be released as soon as its terminal state is published, even before the server joins the returning encoder thread. Its store is removed once and is not retained again after that join. A running recording still refuses release. Known-absent explicit encoder paths fail startup without invented encoder exit details. Protocol version 2, reply shapes, client signatures, queue defaults and encoder environment filtering are unchanged. The real profiled-JPEG video witness requires installed ffmpeg with libx264, mjpeg/h264/rawvideo decoders and image2pipe/rawvideo/MP4 support. Only executable absence produces its named prerequisite skip; an installed tool or missing required codec failing the witness remains a failed test.

Failed discovery or repeated query failure remains unknown, preserves both reasons, and authorizes no signal. Successful re-observation still passes the recorded birth, command and ancestry checks.
