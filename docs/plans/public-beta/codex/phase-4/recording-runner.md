Lane "recording-runner": recording and evidence in the runner, from configuration to the run folder, and a shutdown that saves evidence before it ends processes. Phase 4 items 4 and 6 of docs/plans/public-beta/release-0.1.0.md. Read docs/plans/public-beta/codex/phase-4/common.md first; it binds this lane.

What exists: the runner (src/runner/**: run-session, running-test, browser-pool, native-pool, resources, test-pages), record identity on every event and screenshot (src/protocol/identity.ts, events.ts, evidence.ts), the store and the rebuilt result (src/store/**), `recordSource` and the `FrameSource` contract (src/media/capture.ts) with `frameSource?(identity)` on the session contract, the media client (src/media/client.ts), the reporters, and the replay execution record with its fingerprints (docs/plans/public-beta/replay.md, src/protocol/execution.ts). Today nothing records in a run, and browsers are ended at once at close because there was nothing to save.

Deliver:
1. Configuration: recording is off unless asked; it can be asked for the run and per app; a separate setting says evidence is required, so that a run whose required evidence is missing or incomplete ends with its own named ending and exit status while every test keeps the outcome that was observed. Typed, validated at load, documented in the guide.
2. Lifecycle: one media process per run, started only when something records, checked for readiness and version, restarted once after a crash with the lost recordings named; one recording per app session of each attempt, started before the session's first action and finished after its last check and host check; the media process and its encoders owned and ended by the run under the ownership rule; a lost recording's partial file removed or kept by rule, never left to block a later run.
3. Records: additive events for a recording's start and end carrying the record identity, the capture mode, the frame counts (delivered, sent, dropped, refused, withheld), the status and reason, the artifact's path as a portable reference inside the run folder, and the explicit mapping between the run's clock, the capture's timestamps and the video's time; screenshots keep their capture time and source; the action and check timeline can be laid over the video from the events alone; the replay execution record and its fingerprints are carried unchanged through JSONL and every artifact reference. The result rebuilt from the events still equals result.json, with a test for a recorded run, a failed recording and an interrupted run.
4. Evidence status: per test and per run, apart from the outcome: complete, partial with a reason, unavailable with a reason, not requested. The terminal reporter and the JSONL say it; a media failure, a capture loss, queue saturation, a missed finalization deadline, a cancelled run and a crashed media process each either finalize a usable file or report incomplete evidence, never a silent gap, and never change a verdict.
5. Shutdown: every close path (normal end, failure, interruption, timeout, a lost browser, process exit) first stops the sources, finishes the recordings and waits for finalization under a deadline, then ends the owned browsers, apps and executors, with a bounded forced stop when the deadline passes and the forced stop recorded. The fast close stays the path for a run that records nothing. No orphan process and no unbounded queue on any path; show each with a test.
6. The pixel policy and artifact paths come from the artifacts-policy lane (src/store/artifacts.ts, src/media/policy.ts): build against the signatures the orchestrator sends you and call them; do not write your own path or policy logic.

Files you own: src/runner/**, src/protocol/** (additive), src/store/** except src/store/artifacts.ts, src/config/**, src/api/** where the configuration surfaces, src/reporters/** except src/reporters/html/**, the close ordering in src/browser/{browser,chromium-process}.ts, src/browser/firefox/{browser,process}.ts, src/browser/webkit/{browser,process}.ts and the native session close in src/native/session.ts (small anchored edits, each named in your report), their unit tests, tests/integration/recording-*.test.ts (new), the guide's recording section, docs/plans/public-beta/proofs/recording.md. Do not edit media/**, src/media/**, the drivers' capture files, src/evaluation/**, src/reporters/html/**, src/cli/**.

The media-process lane is moving the client to protocol version 2 and the capture-sources lane is adding sources while you work: start on Chromium with the client and source as they are on disk, and adapt when the orchestrator sends the new signatures. As soon as your event shapes for recordings and evidence status are stable, send the orchestrator a short message (SendMessage to "main") with them: the HTML report lane and the evidence lane build on them.

Gates before you report: `npm run test:unit`, `npm run test:types`, and under the lock `npm run typecheck`, the recording integration files on real Chrome (a passing test, a failing test, an interrupted run, a killed media process, a killed encoder, each with its file decoded independently or its incomplete status asserted), and the existing lifecycle files browser-lifecycle, run-interrupt, m2-guarantees and m2-state to show the close change broke nothing.
