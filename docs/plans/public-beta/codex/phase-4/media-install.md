Lane "media-install": how a host gets the media processor and its encoder. Phase 4 item 8 of docs/plans/public-beta/release-0.1.0.md. Read docs/plans/public-beta/codex/phase-4/common.md first; it binds this lane.

What exists: `retest install` with a pin table, a cache under the user's cache folder, checksums before unpack, a cross-process lock, `--list`, `--verify` and `--json` (src/browser/builds.ts, src/cli/commands/install.ts, src/cli/install/**), `doctor` rows read from the cache (src/cli/doctor/**), the crate in `media/` (edition 2024; the record docs/plans/public-beta/proofs/media.md gives the minimum Rust version, the measured binary size and build time, and lays out the packaging options and ffmpeg options with their costs), the Linux container script `docker/linux/run.sh`, the CI workflow `.github/workflows/ci.yml`.

Decision taken: the release offers a documented, explicit path, never an install script that runs by itself. Shipping prebuilt binaries inside the npm package or as optional platform packages is the founder's later choice; build nothing that forecloses it.

Deliver:
1. `retest install media`: builds `retest-media` from the crate source that ships in the package with the host's cargo (refusing by name a Rust older than the crate's minimum, a missing cargo, or a build with a changed lock file), using the pinned `Cargo.lock` and no network beyond what cargo itself needs for the pinned crates, into Retest's cache with a record (version, source digest, target triple, rustc version, binary sha256); and, as a second way, installs a prebuilt binary from an explicit path or mirror address only when a pinned checksum for that exact build exists, refusing otherwise. `--list`, `--verify` and `--json` cover it like the browser builds.
2. Discovery at run time: the runner finds the media binary through an explicit setting or environment variable first, then the cache record; a missing, damaged, wrong-version or wrong-protocol binary is a setup failure that names what to run, raised only when a run asks for recording; nothing ever falls back to a binary from a Cargo target folder by accident (the developer path is an explicit variable).
3. ffmpeg: a declared prerequisite. An explicit setting or variable names it, else `PATH`; the probe the media process already runs decides whether it can record and with which codec route; a build that cannot record is named with what it lacks. Retest downloads and ships no ffmpeg.
4. `doctor`: rows for the media binary (found where, version, protocol, checksum against its record), cargo and rustc when a build would be needed, and ffmpeg (path, version, licence line, which encoders and muxers the two routes need and whether they are there), each with what to do when it is not right; every suggestion is something the installer or the host's package manager really accepts.
5. Package contents: what the npm package must carry for this path (the crate source, the lock file, licence texts and the third-party crate notices generated from the lock file) listed in `package.json` `files` with one small anchored edit, and a test that packs the package into a temporary folder and builds and runs the media binary from the packed copy alone, with `CARGO_TARGET_DIR` and the cache pointed at fresh folders, to show nothing depends on this checkout.
6. Linux x64: the same path run in the Linux container if Docker is already installed and running here (start nothing system-wide); otherwise recorded unverified with the exact command.
7. Documentation: the guide's prerequisites and installation section, with supported operating systems and architectures, the Rust minimum, the ffmpeg requirement and its licence note, stated plainly.
