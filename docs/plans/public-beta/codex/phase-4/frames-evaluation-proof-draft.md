
## Frames, diagnostics as judge context, races and the corpus

6 October 2026. Release 0.1.0, Phase 4 item 9 ([release-0.1.0.md](../release-0.1.0.md)), lane frames-evaluation. Built against the media client of protocol version 2 ([media-client-v2.md](../codex/phase-4/media-client-v2.md)). Nothing above this section was rewritten; where this section and an earlier one differ, this one describes the tree now (recorded-step evidence, for one, is no longer refused by name).

### What was built

- **Frame evidence.** `test.evaluate` and host checks take `{ recording: { step } }` or `{ recording: { lastMs } }`, with `app`. The parent asks the app's recording (`AttemptRecordings`, which the runner gives the attempt) for the frames of the step's span or of the `lastMs` before the check, on the run's clock, bounded by `maxFrames` (16, and the media process's 64), the image limits and the bytes left (`src/evaluation/frames.ts`). It checks the answer is for the interval asked, that its counts can all be true, and that each frame lies in the interval, in order, within the bounds, with bytes of the format it names. Each frame sent is saved in the run folder and hashed; the record keeps the interval, every frame with its capture time, frame id, fate and file, every stretch with no kept frame with what was lost there and the capture's gap codes, `inInterval`, `available`, `omitted`, the frames not sent, and `status` with `reason`.
- **Frames that are not evidence.** A frame the media process returns as `pending` (a running recording has not placed it) or `unprocessed` (the recording ended without writing it) is never sent. The record names it in `framesNotSent` with its capture time, and the judge is told the stretch from it to the next frame has no picture. A sequence of only such frames leaves the check without evidence: inconclusive, no judge asked, no call spent. Undecodable and out-of-range frames never come back as frames; the media process counts them, and they count as missing.
- **Missing frames, by rule.** A sequence is `complete` only when no frame of the interval was lost (`inInterval` equals `available`), no listed stretch carries a loss or a capture gap code, no stretch went unlisted, the bounds and reads left no kept frame out, every frame returned was placed, the frames were stored through the interval's end, and the media process gave no note that frames may be missing. A stretch in which no frame arrived, as when a page did not paint, is listed and told to the judge but leaves the sequence complete. Over a sequence that is not complete, the parent leaves every criterion the judge passed undecided (`rule: 'frames_incomplete'`, `judgeVerdict: 'pass'`), and the check's reason names the sequence and what it lacks (`settle` in `src/evaluation/judging.ts`). A fail stands: the frame instructions allow a fail only when a frame shows the contradiction. The absence rule from before stands too: over frames, a criterion marked `absence` is never sent to the judge and stays undecided (`rule: 'absence_over_frames'`).
- **No recording, a failed recording, withheld pixels.** A run that does not record the app, and frames the pixel policy withholds, make the check an error; a recording that failed, or a frame store that fails, times out or answers with any status but `ok`, leaves it inconclusive. None lets a required check pass.
- **Diagnostics as context.** `{ diagnostics: 'console' | 'network' | [both], app }` sends the console or network records the attempt kept so far, only when a check names them (`src/evaluation/diagnostics-evidence.ts`): redacted again as the check takes them, the newest `maxDiagnosticRecords` (200), each part's capture state, as one JSON text the judge reads; the exact text is saved and hashed. Parts all unavailable or off leave the check inconclusive.
- **Instructions.** A request with frames is sent the base rules plus the frame rules, version `retest-judge-1+frames-1`; with diagnostics, `+diagnostics-1`. A request with neither is sent the base rules exactly as before.
- **Reports.** A criterion line names the rule that set the judge aside ("shown: inconclusive (the judge said pass, but frames are missing)"); frames evidence is described by its frames and what is missing, diagnostics by the parts and records sent (`src/evaluation/report.ts`). The AI SDK adapter writes a sequence as Retest's account of its interval and stretches, then each frame as an image named by its id and time, and lets the answer cite the sequence or one frame.
- **The corpus.** `fixtures/evaluation-corpus/`: CASES cases (TEXT text, SHOT screenshots, FRAMES frame sequences), each with a requirement, its evidence by file and a label with the reason; the rubric in its README; every label awaiting the founder's review. `scripts/run-evaluation-corpus.ts` runs it against a named judge of a config, three repeats, and reports false passes, false failures, inconclusive and error rates, repeat agreement, latency, usage and the two gates.

### Protocol changes

`schemaVersion` stays 1. Added, all optional: on a frame record `fate`; on an evidence record `framesNotSent` (each `frameId`, `captureUs`, `fate`); on a criterion record `judgeVerdict` and the rule value `frames_incomplete`. With the frame and diagnostics evidence kinds, the two recording selectors, the diagnostics selector, the criterion's `absence` and the host forms added earlier in this lane, all are in the schemas and validated on read. As before, objects in the published schema are closed, so a reader built before these changes refuses a run whose records carry them.
