# WebKit driver

The WebKit half of Phase 3 item 1 of [release-0.1.0.md](../release-0.1.0.md): a WebKit driver behind the session contract, wired into the runner, `doctor` and the config, with the fixed browser suites and the conformance cases run against it. Recorded 5 October 2026 on macOS 27.0 (Darwin 27.0.0), arm64, Node 24.12.0. The [WebKit proof](webkit.md) of Phase 1 is where the client, the build and its missing licence notices were first examined; this record covers the driver built on that route.

## Result

- `src/browser/webkit/` drives Playwright's WebKit build 2359 over its inspector pipe with Retest's own client. No Playwright code is loaded, copied or depended on. The runner runs a test on a `{ browser: 'webkit' }` target; before this lane it refused one at planning.
- The shared page code runs unchanged on WebKit: locator resolution, actionability, the input guard, element queries, the checked state and the page scripts. A bridge (`target-session.ts`) turns each Chrome DevTools command that code sends into WebKit's, and each WebKit answer and error back into the answer and error class the shared code reads. Every protocol difference lives in the driver.
- Conformance after the Mac's restart, on the conformance lane's stricter 148 cases: WebKit 146, 147 and 146 of 148 in three runs, 15 of 15 runs each time; Chrome 146, 148 and 148. On WebKit, F8.1a fails every time on a named refusal (a cell looked up by name, difference 4); A12 (a covered checkbox refused at 499 of 500 ms) failed once, before the fix in difference 9, and passed after; S7 failed once at 1499 of 1500 ms in the shared poll, as Chrome's N5 and F10.5 did in the first run (see What could not be verified). The two defects the conformance fix lane found (lookups refused too widely beside a hidden label; a failure told at 499.x of 500 ms) hold fixed: F7.1 to F7.4 pass in all three runs.
- Element identity for agent references: `WebKitPage` implements `ElementIdentity` as Chromium's page does, `readElements` around the shared keyed look with the lookup refusals `observe` applies, for each locator, and `dispatchTo` through the shared pin. The plan of a multiple select's keys, which reads the select again, plans only from the pinned element and answers `moved` otherwise (`select.ts`, reading the pin from the shared keyed look's own key store).
- The fixed browser suites run on WebKit through `tests/integration/engines.ts`. The declarations compare each differing case with its exact WebKit result; all other cases retain Chrome's result. The independent review completed two consecutive green shared-suite rounds and two consecutive green conformance rounds on all three engines. A fix round on the earlier review's ten findings is recorded below each row and difference it changed.

## Engine differences

Each is what WebKit does, read on build 2359; the driver reports it as it is or refuses by name. None is hidden by a changed assertion. The shared suites and the conformance cases hold every case one of them changes to exactly what WebKit gives, through the declarations in `tests/integration/engine-differences.ts`, each of which cites its item here; a declaration that stops holding fails its case. Items 1, 2, 3, 4 and 6 are declared: the refused connection's message and details, the title in the goto and in the navigation, the move back after a given-up entry, the cell named by its text in conformance F8.1a, and the phone page.

The conformance declarations are limited to cases that normally pass on Chrome. An intentional Chrome failure cannot be relabelled as an engine difference by adding literal text and a source anchor; the resumed review demonstrated that gap with Chrome's A11 record and closed it with a failing-first check.

1. **A failed navigation is told in WebKit's words.** An address nobody answers fails as `not_actionable` with "Could not open http://127.0.0.1:61527/: Could not connect to the server.", where Chrome's says `net::ERR_CONNECTION_REFUSED`. The details are exactly the address with its query removed and `errorText: 'Could not connect to the server.'`. The driver passes WebKit's text on. The shared cases assert that exact message and those details on WebKit. Assert WebKit's own text when checking a refused connection.
2. **A title keeps the control characters `document.title` keeps.** WebKit strips and collapses only ASCII whitespace, as HTML says; Chrome's `document.title` also reads each C0 control character as a space. A title with ESC reaches the parent as `\x9BBell tab \x1B[2J` on WebKit and `\x9BBell tab [2J` on Chrome. The parent cleans both to the same record. The title case of `browser-navigation.test.ts` asserts Chrome's raw text.
3. **WebKit's history stays at an entry it gave up.** A move back onto a response with no content fails at once, naming the address, and the page keeps its document. WebKit's history, though, now stands at the entry it gave up: the next `goto` drops the entries after it, so a later `goBack` returns to that entry, not to the page that stayed (probe: the next goto's page reads `history.length` 3, and the `goBack` after it returns to the entry given up; the same steps in `browser-navigation.test.ts`, which passes on Chrome, go back to the page that stayed). Restoring it would take another navigation, which Retest does not make on its own. In the case for a move back onto a response with no content, the `goto` after the given-up move succeeds, and the next `goBack` goes to the given-up entry, whose address answers with no content again, so it fails as the first did ("The page stayed on …/flip.") and the page keeps the document of that `goto`; on Chrome it returns to the page that stayed.
4. **Roles and names WebKit's tree computes its own way.** Read side by side with Chrome in `webkit-roles.test.ts`: 152 pages of element kinds (the review's probes and the fix round's), each looked up by all 82 roles without a name, plus the named and label lookups of the review's probes and the select options. Where WebKit names an element its own way and the page itself says what Chrome names it, the driver names it as Chrome does, by the element's kind (`chromeRoleOf` in `roles.ts`): a one-option select is a combobox, a number field a spinbutton, an input whose `list` attribute names a `<datalist>` a combobox (unless it is a range or a colour; read from the attribute, since WebKit's own `list` is null for its date fields), a date, time, month or week field and an editable `<div>` or `<span>` with no role nothing a lookup asks for, a `<figcaption>` not a caption. Every other difference is a doubt the reading of the document reports (`accessibility-reading.ts`), and a lookup a doubt could change is refused by name, before any input goes: the role `generic`, always; `img` on a page with an `<img>` without `alt` WebKit leaves out, or an `<svg>` with no role; `option` without a name when the page holds a select's options, and with a name only when one of those options could carry it (its text, `label`, `aria-label`, `title` or `aria-labelledby` text); `group` with a select's option group or an `<hgroup>`; `emphasis` and `strong` with a shown `<em>` or `<strong>`; an option, list item or tree item outside its listbox, list or tree, and the role WebKit kept it as; an element whose role attribute WebKit overrode, both roles; every role on a page with an editable element other than a `<div>` or `<span>`; names of a cell, grid cell, column or row header or tooltip when one of them has no `aria-label` or `aria-labelledby`; names of every role a `<label>` names when a hidden `<label>` labels a control; a table WebKit reads as a layout table. On the table after the restart, with the shown-label case: 12581 lookups, 12189 answered as Chrome answers, 392 refused by name, none answered differently. A cell named by `aria-label`, and a custom option beside a native select, are now answered.
Conformance F8.1a asserts `error`, class `unsupported`, at `toBeVisible` on the cell named Grace Hopper, with detail `role: 'cell'` and at once. Its literal message is "Could not look up getByRole('cell', { name: 'Grace Hopper' }): Chrome names a cell from its text, and WebKit's accessibility tree does not, so Retest refuses the lookup rather than find less on WebKit. Find it with getByText() or getByTestId(), or by its position with nth()." A cell with an explicit accessible name remains usable.

5. **A select of several options never passes through one nobody asked for.** WebKit's list chooses with Home, End, Shift and the arrows, and every key the page hears as a change. The plan starts from the first option asked for with Home when it is the list's first, or from the last with End when it is the list's last, and widens over the options asked for only; one option before them is passed only when the list already holds it alone. A set with a gap, or one away from both ends, is refused by name before any key is sent. `webkit-driver.test.ts` logs every `input` and `change` of such a list and holds each to the options asked for.
6. **No phone or touch screen.** A WebKit target takes a viewport, a pixel ratio and a user agent. A mobile layout or a touch screen is refused at setup as `unsupported` with exactly "Retest's WebKit driver cannot emulate a mobile layout or a touch screen. Give this WebKit target a viewport, or a screen with isMobile and touch false." The touch input path is not built for WebKit, so `tap` is refused too. The phone case of `browser-actions.test.ts` asserts that exact refusal. Use a desktop viewport; this does not verify a phone layout.
7. **Console and network cover the document and its frames.** Build 2359 renders a page's frames of every site in the page's own web process, so their console messages and requests reach the page's target; each request names its frame, and each console message its script, which WebKit's debugger names the context of (the page turns the debugger on with every pause off; measured: no cost to a page's script, and `debugger;` does not stop). The scope covers the document and frames of either site; workers are not followed, and a worker's request, which WebKit sends on the page's target under the worker's id, is left out. A message with no time of its own is counted unread rather than given the parent's clock.
8. **The helpers run outside the browser's process group.** Networking, GPU and web content processes are XPC services launchd starts, with parent pid 1 and groups of their own. The driver attributes each to its browser with `launchctl print pid/<browser pid>` while the browser runs, records it by pid, start time and command, and ends only what it recorded, after checking the record still matches. A home with a record file lets the next launch sweep what a killed Retest process left, and leave a live one alone. The sweep compares a recorded process with `sameProcessIdentity` from `src/shared/process-ownership.ts`: the same pid and start time, a command line that macOS reads as the process's kernel name in parentheses while it exits counted as unreadable rather than different, and two readable command lines that differ still refused (`webkit-sweep.test.ts`). Every other check of a recorded process goes through `OwnedProcessGroup`, which uses the same rule. A helper whose command line cannot be read when launchd first lists it is not recorded, so it is never signalled. A reading that fails is no proof either way: `processStartedAt` tells "no such process" (a whole `ps` reading without the pid) from "could not read" (it throws), and the sweep leaves a home whole, signalling nothing, when the Retest process that made it or any recorded process could not be read, and while any process has the pid of a Retest process whose own start was never read.
9. **A timeout is told only once its budget has passed.** A poll's last look waits all but a moment of its budget for the page to change, then reads. A timer can fire a fraction of a millisecond early by the clock, and a read that timed out at such a moment reached the caller before its deadline, which then took it as the failure of the check: S8 in one of the conformance lane's runs, and `toHaveURL` in one run of `webkit-lookup` here, each ended `timeout` instead of `check_failed`. The WebKit page now waits out the rest of the budget before it answers a timeout. Measured with 200 such last looks per engine on one machine: before the change, WebKit answered 2 timeouts before the budget had passed and Chrome 1; after it, WebKit answered none and Chrome, unchanged, 3. Chrome's page has the same race. The same holds for a refusal at the end of an action's time: a failure that is a timeout, or that says it waited the whole budget (`details.waitedMs`), is told only once that budget has passed by the clock (`waitedWholeBudget` in `page.ts`), since the browser call that ended the last look can time out more than a millisecond early, while the deadline still reads time left. Seen after the restart in a conformance run: A12, a covered checkbox, refused after 499 of its 500 ms. `webkit-driver.test.ts` holds 100 refusals of a hidden button and 100 of a covered checkbox to their 60 ms budget; on the code before this round one of the hundred hidden-button refusals came at 59.753 ms.
10. **Looks at once take the page target in turn.** Every `DOM.getDocument` gives every node of the document a new id, so two looks once shared a half-cancelled document: 400 buttons were counted as 0, 100, 200 or 300, or a look threw. The document is now asked for once per world, each look holds its target's turn from its reading to making each element it found an object, a node the page removed is read again rather than left out, and a look that keeps losing its reading until its budget is spent fails as a named timeout, never as fewer elements.

## Changes needed outside this lane

Additive, and not made here, since the files are not this lane's:

1. **A capture source name for WebKit.** Done by the runner fix lane; the frame source now implements `FrameSource`.
4. **A time source for a console record.** `src/diagnostics/observations.ts` has no way to say a record's time is the parent's; until it has, a WebKit console message without a timestamp is counted unread rather than kept with the parent's clock.
5. **The protocol of a response.** WebKit gives a request's protocol only with `Network.loadingFinished`, and `FinishedObservation` has no field for it, so WebKit's responses name none; the scope's reason says so.
2. **The build in a target's identity.** `TargetInfo` could carry `{ build, version, protocolSha256 }` for a WebKit target. `browser.started` names the version and build in one string today.
3. **The early timeout on Chrome.** `src/browser/page.ts` could wait out its budget before telling a timeout, as the WebKit page does now, or `src/assertions/look-until.ts` could take a last look's timeout as the deadline when the look's budget was all the time left.

## What could not be verified

Most important first.

1. **A check that gives up a fraction of a millisecond early, in the shared poll.** `src/assertions/look-until.ts` stops once less than a whole millisecond is left (`deadline.expired`, line 76), after a last look whose wait was cut to the whole milliseconds left (line 56), so a check can fail at 1499.x of 1500 ms: S7 on WebKit in one conformance run here, N5 and F10.5 on Chrome in another. The page holds what it answers to its budget (difference 9); the poll's own end is shared code, not this lane's.
2. **The pinned list plan on a page that swaps its select between the look and the plan.** The plan's pin is shown on the real build by calling the plan directly with another list's key, and end to end through `dispatchTo`; a page swapping the select in the moment between the two calls was not produced.
3. **The hold of difference 9 failing on the code just before it.** The early refusal it closes was seen once on the real build (A12 at 499 of 500 ms); the timer firing early cannot be forced, so the unit case holds the rule, and the real-build case of 200 refusals passes on today's code but was not run on the code between the fix round and this change.
4. **AI checks over WebKit captures.** A WebKit failure screenshot is captured and named `webkit`; no judge has looked at one.
5. **The cross-platform reference flow with WebKit**: another lane's work, not run here.
6. **The same early-timeout race on Chrome.** Chrome's page still tells a poll's last look, and a failure at its deadline, a fraction of a millisecond early; the fix belongs in the Chromium driver or the poll.
7. **Role lookups beyond the table.** The role table holds 152 pages of element kinds and the review's named lookups; an element kind outside it is answered by WebKit's tree as the driver reads it, and may differ from Chrome's without a doubt for it.
8. **Phone and touch emulation**, and `tap`, are not built for WebKit.
9. **A web content process killed under a running page**, as opposed to the whole browser, was never tried.
10. **Other builds and machines.** Only build 2359 for macOS 26 on arm64, on macOS 27.0. WebKit on Linux is refused by design.
11. **The preferences file.** `~/Library/Preferences/org.webkit.Playwright.plist`: nothing in the driver stops cfprefsd writing there.
12. **The browser's output not closing in time** (held item 4). The cause found for Chrome's twin, a timer racing an output close that needs several event-loop turns, is fixed here the same way, with a unit case that fails on the old code; the single `cleanup_failed` conformance run of the driver lane was not reproduced on the real build.
13. **The diagnostics lane's unit contract for a message with no time.** `tests/unit/diagnostics-engines.test.ts` (lines 242-243) sends WebKit's "required" console message without `timestamp`, which WebKit's protocol leaves optional, then expects a record carrying the engine's time (line 291) and a complete console (line 321). The collector counts such a message unread rather than give it the parent's clock, so two WebKit cases fail there; real messages of build 2359 carry a time, and `diagnostics-engines` on the real build passes 30 of 30. The file is the diagnostics lane's.
