Lane "capture-sources": real frames from all five targets into the media processor. Phase 4 item 2 of docs/plans/public-beta/release-0.1.0.md. Read docs/plans/public-beta/codex/phase-4/common.md first; it binds this lane.

What exists: the `FrameSource` contract, `CaptureMode`, `recordSource` and their stats in src/media/capture.ts; the Chromium source on `Page.startScreencast` in src/browser/capture.ts, shown feeding the real media process (docs/plans/public-beta/proofs/identity.md); the WebKit driver's capture file src/browser/webkit/capture.ts and the Firefox driver (read docs/plans/public-beta/proofs/{webkit-driver,firefox-driver}.md for what each engine's protocol offers); native screenshots from the executor and the window crop on macOS (src/native/**, docs/plans/public-beta/proofs/native.md; the executor's own screen stream is deliberately closed by holding its port and stays closed); `frameSource?(identity)` on the session contract in src/browser/contract.ts; the capture source names in src/protocol/identity.ts.

Deliver a `FrameSource` for each of Chromium (keep, refine only on evidence), Firefox, WebKit, the iOS simulator and a macOS app, each reached through the session contract's `frameSource`:
1. For each target, find out on the real target which capture modes exist and what each really gives (a pushed stream of frames from the engine or the OS, a recording the platform makes itself, or a loop of screenshots), measure the cadence it reaches on a page or screen that changes on every tick, and choose the best mode that is honest. Name each mode truthfully in `CaptureMode` (additive names; a screenshot loop is `screenshot-loop` and is never described as a live stream; a recording the platform encodes itself is its own mode with its own limits on timeline mapping). On macOS, a mode that needs a system permission is offered only when the permission is already granted, is refused by name otherwise, and never prompts; say which permission.
2. Keep encoded frames encoded: hand the media process the bytes the target produced (PNG or JPEG) without re-encoding in Node.
3. Every frame carries the record identity and a timestamp on the run's clock; the mapping from the target's own clock to the run's clock is explicit and recorded; frames on another clock, out of order or too large are refused and counted, as `recordSource` already does.
4. Capture status is explicit per target: available with its mode, or unavailable with its reason; a source that starts and then loses its target ends with a named reason; frames withheld by the pixel policy (another lane provides the policy; expose a way to suspend and resume a source and count the withheld stretch) are counted apart from dropped frames.
5. Prove each source on its real target: a fixture that changes visibly on every tick (the task app for browsers, TaskPhone and TaskDesk for native), frames fed through `recordSource` into the real media process, the file decoded independently, and each decoded frame matched to the screen state its timestamp maps to (the method the Phase 1 media proof used), with the measured cadence, drops and gaps recorded. A target whose capture cannot be exercised here is recorded unverified with the reason, never as supported.
6. Starting and stopping a source never disturbs the test: no action is delayed past its budget by capture, a stop is bounded, and a source left running at close is ended by the session's own close.
